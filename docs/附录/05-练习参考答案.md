# 附录 E · 练习参考答案（要点版）

> **这是「要点」不是「标准答案」。**
> 本教程的练习大多是**开放式**的——没有唯一解，只有"说没说到点上"和"跑没跑通"。
> 所以下面给的是两样东西：**关键点**（你该提到什么）和**验收标准**（怎么算做完了）。

## 怎么用这份答案

| 阶段 | 做法 | 效果 |
|:--|:--|:--|
| **① 先做** | 不看答案，自己写/自己跑，卡住先回读对应小节 | 暴露真实的理解缺口 |
| **② 再对** | 只对照"关键点"，对不上就标记，不要立刻看下一行 | 知道自己缺的是概念还是细节 |
| **③ 回读** | 只回读标记的那一小节，而不是重读整章 | 节省时间，定位精准 |
| **④ 重做** | 合上答案再做一遍 | 唯一能确认"真的会了"的方式 |

> 动手题的答案写成了**验收标准**——能通过验收就是对的，写法可以和你不一样。

## 第一部分 · 入门基础

### 1.1 AI Agent 导论

1. **Chatbot / Workflow / Agent 的区别** —— 判据是"**谁决定下一步**"：Chatbot 只回答不动手；Workflow 的步骤由开发者写死；Agent 由模型在运行时决定调什么工具、调几次。例子：FAQ 问答机器人 / 固定审批流 / 自己查天气再算穿衣的助手。
2. **三个可用 Agent 解决的问题** —— 判据是"**这一步是否需要当场判断**"。需要判断的（找资料、写初稿、决定先查哪个库）交给 LLM；不需要判断的（发邮件、落库）写成确定性代码。
3. **MCP 解决了什么** —— 把"模型怎么连工具/数据"标准化：工具方实现一次 Server，所有客户端都能用，M 个模型 × N 个工具从 M×N 降到 M+N。称"AI 世界的 USB-C"是因为它统一了接口，让"设备（工具）"与"主机（Agent）"解耦。
4. **Workflow / Agent 划分图** —— 验收：每个菱形判断节点都能说出"为什么不能预先写死"；能写死的分支就不该给 Agent。

### 1.2 开发环境搭建

1. **跑通示例** —— 验收：能完成至少一轮对话，且 `LLM_*` 从 `.env` 生效。
2. **`uv init` 新项目** —— 验收：5 行脚本能打印中文回复，`uv run` 不报 `ModuleNotFoundError`。
3. **锁文件解决什么** —— `pyproject.toml` 只写版本**范围**，`uv.lock` 锁定这次解析出的**确切版本 + 哈希**，保证换机器、换时间装出同一套依赖（可复现构建）。
4. **切换 `OPENAI_*`** —— 回退逻辑是 `os.getenv("LLM_API_KEY") or os.getenv("OPENAI_API_KEY")` 这类"或"链。要同时维护两套 Key：按 provider 建**两个 model 实例**，用配置项选一个，而不是在一个实例里混用两套 env（否则 base_url 与 key 会错配）。

### 1.3 第一个 Agent

1. **换成自己的工具** —— 验收：消息里出现 `AIMessage.tool_calls`，是**模型自己决定**调的，不是你代码里直接调用。
2. **连续两轮工具调用** —— 验收：消息序列出现两次 `AIMessage(tool_calls)` + `ToolMessage` 交替，第二轮用到了第一轮的结果。
3. **带记忆的流式命令行 Agent** —— 要点：`create_agent(..., checkpointer=InMemorySaver())` + `config={"configurable": {"thread_id": "cli"}}`；输出用 `stream(..., stream_mode="messages")` 逐块打印。
4. **研究助手多了什么** —— 多工具协作（搜索 + 落盘）、`system_prompt` 规定工作流、报告写文件、模型配置从环境变量读。

## 第二部分 · 核心概念

### 2.1 Prompt 工程与上下文工程

1. **Zero-shot vs Few-shot** —— 验收：Few-shot 输出更贴格式；记录差异点（结构、边界情况处理、语气）。
2. **用 checklist 优化 Prompt** —— 三个维度：**明确性**（说清输入输出与边界）、**约束**（禁止事项、必须格式）、**信噪比**（删掉与任务无关的背景）。
3. **`response_format=ToolStrategy(Model)`** —— 要点：传 Pydantic 模型，结果从 `result["structured_response"]` 取，直接是实例而非 JSON 字符串。
4. **反例实验** —— 预期：4000 token 冗余版准确率下降、耗时上升。解释：注意力被无关内容稀释（context rot），**有效信息密度**下降。

### 2.2 Chain 模式详解

1. **翻译 + 总结** —— 验收：`prompt1 | llm | prompt2 | llm` 顺序执行，中间结果可打印。
2. **并行 Chain** —— 要点：`RunnableParallel(sentiment=..., keywords=...)`，输出 dict 同时保留 `original`。
3. **回退 + 条件分支** —— 要点：`primary.with_fallbacks([backup])`；分流用 `RunnableBranch` 或路由函数（含"投诉"关键词走投诉链）。
4. **为什么不适合纯 LCEL** —— LCEL 是 **DAG（无环）**，步数与顺序在编译期确定；"模型自己决定调几次工具"需要**环**，只能交给 Agent / LangGraph。

### 2.3 Agent 核心架构

1. **为什么更适合不确定任务** —— 判据：路径不可预知、需要多步试错。不适合用 Agent 的场景：固定表单校验、单次文本分类（用 Chain 更快更稳更便宜）。
2. **打印消息序列** —— 验收：能标出 `AIMessage.content`（Thought）→ `AIMessage.tool_calls`（Action）→ `ToolMessage`（Observation）的交替。
3. **`StepGuardMiddleware` 限 3 步** —— 验收：第 4 步抛错或提前终止，且计数可见。
4. **对比实验** —— 结论应体现：LCEL 代码短、路径固定、可预测；Agent 灵活但不可预测，需要护栏与上限。

### 2.4 记忆机制

1. **`InMemorySaver` 会话记忆** —— 验收：同 `thread_id` 记得上文，换 `thread_id` 立刻忘记。
2. **三种长对话策略** —— 完整列表：token 线性增长；`trim_messages`：保留最近 N 条，早期信息直接丢；`SummarizationMiddleware`：压缩成摘要，信息有损但省 token。
3. **用户画像长期记忆** —— 要点：`store.put((ns,), key, {...})` 写入、`store.search((ns,), query=...)` 检索；新会话先检索再拼进 system prompt。
4. **盲目采信记忆的错** —— 例：三个月前说"我讨厌长回复"，如今换了场景仍被压成一句话。防范：记忆带**时间戳与置信度**、关键事实**实时校验**、记忆只当 hint 不当事实。

## 第三部分 · LangChain v1 实战

### 3.1 LangChain v1 核心组件

1. **两步工具调用** —— 验收：先搜索再计算，两轮 `tool_calls`。
2. **`SummarizationMiddleware`** —— 验收：压缩后 `len(result["messages"])` 下降，且摘要里保留了关键决策。
3. **`ToolStrategy(Model)`** —— 验收：`result["structured_response"]` 是 Pydantic 实例。
4. **自定义 `AgentMiddleware`** —— 要点：`before_model` 里注入当前时间；`@before_model` 装饰器版代码更短，但**一个类可复用多个 hook**，适合成组逻辑。

### 3.2 模型调用与工具

1. **`init_chat_model` + invoke/stream** —— 验收：stream 逐块吐出，invoke 一次返回完整结果。
2. **三工具 + 异常兜底** —— 要点：`@wrap_tool_call` 捕获异常返回友好文本，让模型能继续推理而不是崩掉。
3. **`args_schema` + `ToolRuntime`** —— 要点：参数用 Pydantic 校验；`context_schema` 定义后 `invoke(..., context={"user_id": ...})`，工具内读 `runtime.context.user_id`。
4. **三种结构化输出策略** —— ToolStrategy 走一次工具调用（多一轮）；ProviderStrategy 用模型原生结构化输出（消息更少）；AutoStrategy 按模型能力自动选。

### 3.3 向量存储与检索

1. **Chroma 持久化** —— 验收：重启程序后 `similarity_search` 仍能命中。
2. **`similarity_search` vs MMR** —— MMR 牺牲部分相关性换**多样性**，避免返回一堆同质文档。
3. **元数据过滤** —— 要点：`filter={"category": "x"}`；`similarity_search_with_relevance_scores` 看分数分布来定阈值。
4. **接入 Agent** —— 观察点：Agent 常换 2–3 组关键词重试，说明**工具描述与返回格式**直接决定它会不会重试。

### 3.4 构建聊天 Agent

1. **最简单的聊天 Agent** —— 验收：3 轮对话可运行。
2. **加 `InMemorySaver`** —— 验收：第二轮能引用第一轮说过的内容。
3. **记忆 + 工具 + 流式** —— 验收：三者同时生效（记得上文、能调工具、逐字输出）。
4. **换 `SqliteSaver`** —— 要点：`SqliteSaver.from_conn_string("checkpoints.db")`，重启后同 `thread_id` 记忆仍在。

### 3.5 实战：研究助手

1. **跑通并观察** —— 验收：看到 `search_web` → `save_report` 的调用顺序。
2. **换真实搜索 API** —— 要点：只改函数体，**签名与 docstring 不变**，返回值仍是字符串（模型要能读）。
3. **加专家评审** —— 要点：写完报告后让第二个 LLM 打分，不达标就带着评审意见重写一轮。
4. **`store` 跨会话记忆** —— 要点：把 `store` 传给 `create_agent`，下次研究先检索历史结论。

## 第四部分 · LangGraph 进阶

### 4.1 LangGraph 基础

1. **三节点顺序图** —— 验收：打印 A → B → C 顺序。
2. **`print_ascii` / `draw_mermaid`** —— 要点：`get_graph().draw_mermaid()` 返回字符串，粘到支持 Mermaid 的渲染器即可。
3. **`counter` 字段** —— 验收：最终值 = 节点数。若不加 `operator.add` reducer，后写会覆盖前写，结果恒为 1。
4. **`stream_mode="updates"`** —— 验收：每节点一个 chunk；`invoke` 只给最终 state。

### 4.2 状态管理与节点

1. **5 字段 State** —— 验收：三节点各更新不同字段，最终 state 齐全。
2. **`operator.add` vs `add_messages`** —— 前者对列表是**拼接**；后者按 `id` **去重/更新**，同 id 会替换而不是追加。
3. **`store` 用户画像** —— 要点：`store` 独立于 `checkpointer`，换 `thread_id` 仍生效（这才是"长期"）。
4. **`get_state_history`** —— 要点：返回每步 checkpoint；可用 `update_state` 改状态，或从某个 checkpoint 重新 `invoke` 重放。

### 4.3 路由与循环

1. **情感分析 → 条件路由** —— 验收：正/负向走不同分支。
2. **`Command` 与 `Send`** —— 要点：`Command(goto=..., update=...)` 由**节点自己**返回决定跳转；`Send` 用于 map-reduce，把一批输入**并行**分发给同一节点。
3. **手写 ReAct 图** —— 要点：`agent ⇄ tools` 两节点 + 条件边；`ToolNode` + `tools_condition` 等价但省掉路由代码。
4. **`ns` 的差异** —— 要点：`ns` 是命名空间元组，子图内事件带子图名前缀，用于区分"谁发的"。

### 4.4 子图

1. **3 节点子图** —— 验收：主图调用子图，子图 schema 是主图子集。
2. **独立 schema** —— 要点：父图与子图字段不同时，加**映射节点**做双向转换。
3. **同一子图挂两处** —— 要点：reducer 要能区分来源（带节点名的 key，或列表拼接后去重），否则结果互相覆盖。
4. **`part["ns"]` 标识子图** —— 要点：出现 `("subgraph_name",)` 前缀。

### 4.5 实战工作流 Agent

1. **观察中断** —— 验收：看到 `__interrupt__`，`Command(resume=...)` 后继续执行。
2. **真实 LLM 生成章节** —— 要点：占位文案换成 `llm.invoke(prompt)`，prompt 里带研究摘要。
3. **`Send` 并行写作** —— 要点：`Send("write_section", {...})` fan-out，state 字段用 `operator.add` 汇总。
4. **`SqliteSaver` 跨重启恢复** —— 验收：中断 → 退出程序 → 重启 → 同 `thread_id` 能恢复。

## 第五部分 · RAG 系统

### 5.1 RAG 原理

1. **RAG 为什么缓解幻觉** —— 把"事实"从参数里挪到检索结果，模型只做归纳并给出处。**不能**解决：推理能力不足、检索不到的问题、多条冲突信息的裁决。
2. **RAG vs 微调** —— 政策频繁变更时，微调要重训且易过时；RAG 改文档即刻生效，还能给出来源。
3. **故意问知识库外的问题** —— 验收：Agent 要么换关键词再检索，要么明确说"未找到"，**不能编造**。
4. **`to_context(entity)`** —— 要点：把实体 + 关系拼成文本，提示词要求"标注来源实体"，这样答案可溯源。

### 5.2 文档处理

1. **`RecursiveCharacterTextSplitter`** —— 验收：每块带 `source` 与序号元数据。
2. **200 vs 1000** —— 200：块多而碎，语义不完整、召回噪声大；1000：块少但混入无关内容，精度下降。
3. **父子块** —— 要点：用子块检索（精准），命中后按 `parent_id` 回溯父块（上下文完整）。
4. **`PyPDFLoader` 的 metadata** —— 通常含 `source`、`page`、`source_type` 等字段。

### 5.3 向量数据库

1. **Chroma 建库 + 3 次查询** —— 验收：3 次查询都有结果，重启后仍在。
2. **Chroma vs FAISS** —— FAISS 纯内存检索更快；Chroma 自带元数据过滤与持久化，工程上更省事。
3. **Qdrant 嵌入式 + 过滤** —— 要点：`QdrantClient(path=...)` 本地模式；过滤用 `FieldCondition`。
4. **分数分布定阈值** —— 要点：不同查询的分数分布差异很大，阈值应按语料/查询类型定，**不要全局写死**。

### 5.4 优化策略

1. **`QueryRewriter`** —— 验收：口语化查询被改写成含具体技术词的检索式。
2. **纯向量 vs 混合检索** —— 混合对**专有名词、代码片段、罕见词**更稳；纯向量容易漏掉字面匹配。
3. **重排的收益** —— 要点：Cross-Encoder 重排通常显著提升 MRR/NDCG，代价是延迟上升（先粗召回 20–50 条再重排）。
4. **RAGAS** —— 要点：需要 ground truth；`faithfulness` 看答案是否被上下文支撑，`context_recall` 看该召回的有没有召回。

### 5.5 企业级知识库

1. **跑通 `main()`** —— 验收：能答出文档内容。
2. **增量更新** —— 要点：`manifest.json` 记录块哈希，只有变化的块被重建。
3. **文档级 ACL** —— 要点：检索前按 `user_roles` 过滤 `metadata.acl`；**先过滤再算相似度**（后过滤容易在日志/缓存里泄露）。
4. **FastAPI + 角色演示** —— 验收：不同 `user_roles` 看到不同来源列表。

### 5.6 RAG 评估

1. **对照 `eval.py` 的判定** —— 验收：逐条比对原文，判定与直觉不一致的地方，要么修 `GOLDEN`，要么修判定逻辑。
2. **负样本** —— 要点：负样本应判"拒答"；指标用**正确拒答率**（或把"拒答"当成一类标签算准确率），而不是硬算命中率。
3. **`nDCG@k`** —— 要点：nDCG 带位置折损，k 越小越严格；k=1 时 MRR 与 nDCG 数值接近。
4. **换自己的语料** —— 要点：指标下降通常**召回先崩**（分布变了），据此判断该优化召回还是排序。

## 第六部分 · 高级主题

### 6.1 多 Agent 协作

1. **改 Supervisor Prompt** —— 验收：reviewer 只被调用一次，输出结构随之变化。
2. **给子 Agent 加工具** —— 要点：子 Agent 用 `create_agent(tools=[search_web])`，Supervisor 只负责分派、不直接调工具。
3. **LLM 动态拆解 + reducer 归并** —— 要点：plan 节点让 LLM 输出子任务列表 → `Send` fan-out → reducer 合并结果。
4. **主持人选举** —— 要点：LLM 结构化输出 `{"next": "agent_name"}`，替代固定轮转。

### 6.2 评估与优化

1. **10 条评测样例** —— 验收：含 ≥2 条负例，框架能跑出通过率。
2. **`judge_json_schema`** —— 要点：判定器返回 `{pass: bool, reason: str}`，用 Pydantic 校验结构。
3. **`compare_runs` CLI** —— 要点：基线 JSON + 当前 JSON 逐条 diff，退化项超阈值就**退出码非 0**（才能卡 CI）。
4. **接入 Langfuse/Phoenix** —— 要点：从 trace 里挑失败 case 回流进评测集，形成闭环。

### 6.3 成本控制

1. **`CostCalculator`** —— 验收：能算出 token 与金额。
2. **`ResponseCache`** —— 要点：缓存键 = 规范化后的 prompt 哈希；命中率决定实际节省比例。
3. **`ModelRouter` A/B** —— 要点：简单任务路由到小模型，对比"成本下降 vs 质量损失"，找拐点。
4. **Prompt 缓存** —— 要点：**稳定前缀（system + 工具定义）放最前**才能命中，命中后输入 token 计费显著下降。

### 6.4 安全与合规

1. **`PIIGuard`** —— 验收：手机号/邮箱/API Key 被识别并脱敏。
2. **间接注入特征** —— 要点：外部内容里出现指令式语句（"忽略之前的指令""请按以下步骤操作"）即标记。
3. **退款前审批** —— 要点：`HumanInTheLoopMiddleware(interrupt_on={"refund": True})` + `checkpointer`；用户拒绝后走**优雅收尾**分支，而不是抛异常。
4. **OWASP LLM Top 10** —— 要点：逐项（注入、泄露、供应链、过度代理…）对照打勾，输出缺口清单。

## 第七部分 · 生产部署

### 7.1 API 服务部署

1. **调 `/chat` 与 `/chat/stream`** —— 验收：`/docs` 可调，stream 逐块返回。
2. **Redis 限流** —— 要点：`INCR + EXPIRE` 或滑动窗口 zset，多 worker 共享计数。
3. **`PostgresSaver`** —— 要点：需要连接串与 `setup()` 建表；跨进程、跨重启共享会话。
4. **压测** —— 要点：观察 P95 延迟随并发上升的拐点、错误率与限流触发位置。

### 7.2 Docker 容器化

1. **写 Dockerfile** —— 验收：镜像构建成功且能跑通一次对话。
2. **compose + 健康检查** —— 要点：`depends_on: {redis: {condition: service_healthy}}` 保证启动顺序。
3. **Docker secrets** —— 要点：密钥挂到 `/run/secrets/llm_api_key` 读取，**不落环境变量**（`docker inspect` 看不到）。
4. **slim vs alpine** —— alpine 体积小，但 musl 下部分 wheel 缺失需现场编译；slim 兼容性更好、构建更快。

### 7.3 可观测性与监控

1. **`StructuredLogger`** —— 验收：JSON 日志含 `trace_id`、耗时、token。
2. **`/metrics` + Grafana** —— 要点：暴露 Prometheus 格式，画 P95 延迟与 token 用量。
3. **OTel span 树** —— 要点：一个 span 包住整次 `invoke`，子 span 覆盖每次模型/工具调用。
4. **告警规则** —— 要点：设错误率阈值，人为制造 5xx 验证触发与恢复。

### 7.4 CI/CD 流水线

1. **`ci.yml`** —— 验收：PR 触发 lint + test。
2. **评测接入 CI** —— 要点：评测作为独立 job，`eval_gate.py` 不达标**退出非 0**。
3. **`canary.sh` / `rollback.sh`** —— 要点：灰度 5% → 观察指标 → 超阈值自动回滚。
4. **matrix 策略** —— 要点：`strategy.matrix.python: ["3.12", "3.13"]` 并行。

## 第八部分 · 生态与选型

### 8.1 核心框架对比

1. **3 个框架跑通官方示例** —— 验收：都能跑，记录各自的抽象层次差异。
2. **场景匹配** —— 判据：是否需要显式状态机、多 Agent、人工介入、可回放。
3. **用 LangGraph 实现 handoff** —— 要点：条件边 + 把控制权与必要上下文交给下一个 Agent 节点（不是简单函数调用）。

### 8.2 多 Agent 模式

1. **平等对话模式** —— 要点：群聊式共享消息，用 reducer 汇总发言，轮转或选举决定 `next`。
2. **MAF vs CrewAI** —— 验收：两家 demo 都跑通，记录 API 风格（声明式 vs 角色式）差异。
3. **何时辩论优于协作** —— 需要**多视角对抗**时：方案评审、红蓝对抗、有明确对错但易被单一路径带偏的任务。

### 8.3 工具生态

1. **LiteLLM 替换** —— 验收：只改模型名/配置即可切换，业务代码不动。
2. **3 个 MCP Server** —— 验收：接入后 Agent 能调用，且工具描述清晰。
3. **电商客服工具流** —— 要点：查单（顺序）→ 判断是否退款（条件）→ 并行查物流与库存。

### 8.4 记忆系统对比

1. **替换为三层架构** —— 验收：短期（会话）/长期（事实）/画像（偏好）各就位。
2. **Chroma vs Qdrant** —— 要点：Chroma 单机省事；Qdrant 在过滤、规模、并发上更强。
3. **学习用户偏好的记忆系统** —— 要点：会话层 / 事实层 / 偏好层，各自要有写入时机与过期策略。

### 8.5 低代码平台

1. **Dify 复刻 3.4** —— 验收：能对话，记录开发耗时与可定制性差异。
2. **RAGFlow 复现 RAG** —— 验收：同一批文档问答，对比召回质量。
3. **选低代码的判据** —— 需求稳定、维护者非研发、需要快速验证 → 低代码；需要深度定制、复杂权限、性能敏感 → 编码。

### 8.6 领域专属 Agent

1. **5 个必备工具** —— 验收：工具与该领域强相关（如医疗：指南检索、药物相互作用、剂量计算）。
2. **构建 `DomainAgent`** —— 验收：RAG 知识库 + ≥2 个专用工具可跑。
3. **医疗 vs 金融的安全约束** —— 医疗重**不可逆伤害**（宁拒答不乱答、必须可追溯）；金融重**合规与留痕**（审计、双人复核、话术边界）。

### 8.7 评估工具

1. **DeepEval 5 个用例** —— 验收：能跑出分数与失败原因。
2. **`AgentMonitor`** —— 要点：埋点延迟/成本，聚合到看板。
3. **PR 自动评估** —— 要点：评估 job 挂在 PR 上，退化则阻断合并。

### 8.8 安全沙箱

1. **输入检测** —— 验收：注入样例被拦或降级处理。
2. **Docker 沙箱** —— 验收：网络禁用、内存上限、只读文件系统三项都真实生效。
3. **泄露审计** —— 要点：检查日志与返回里是否带内部路径、密钥、系统提示词。

### 8.9 技术选型指南

1. **业务建模模板** —— 验收：填完，含业务约束、规模、合规要求。
2. **选型矩阵** —— 要点：3 个方案 × 权重评分，给出结论**和风险**。
3. **3 个月路线图** —— 验收：含里程碑与每个里程碑的验收标准。

### 8.10 MCP 协议完全指南

1. **2 个工具的 stdio Server** —— 验收：客户端能 `list_tools` 看到两个工具。
2. **`MultiServerMCPClient` 接入** —— 验收：`get_tools()` 返回工具并成功挂到 Agent。
3. **Streamable HTTP + OAuth** —— 要点：HTTP 传输 + Bearer token 校验中间件。
4. **MCP vs 自写 `@tool`** —— MCP 版换客户端即可复用、跨语言跨项目；自写版改一处要改所有项目，但更轻、无进程开销。

### 8.11 A2A 协议与互操作

1. **A2A 与 MCP 的区别** —— MCP 管 **Agent ↔ 工具**，A2A 管 **Agent ↔ Agent**；互补关系，一个 A2A Agent 内部仍可用 MCP 连工具。
2. **Agent Card** —— 验收：含 name、description、skills、endpoint。
3. **A2A SDK 暴露远端 Agent** —— 验收：另一端能发现并调用你的 Agent。
4. **主管 + 3 子 Agent** —— 验收：任务分派走 A2A，子 Agent 各自持 MCP 工具，图能标出两条协议的分界。

## 第九部分 · Agent Harness

### 9.1 什么是 Agent Harness

1. **为什么说"我做了个 Harness"** —— 模型只提供推理，"Agent 的行为"由提示词、工具、权限、循环、验证共同决定，这些都在模型之外。马具类比：**马决定力气，马具决定方向与可控性**；OS 类比：应用跑在 OS 上，资源调度与权限由 OS 管。
2. **数据推演** —— `0.97^15 ≈ 63.3%`；`0.99^15 ≈ 86.0%`。结论：单步小改进被**指数放大**，所以验证与重试是最高 ROI 的 Harness 投入。
3. **拆解一个编码工具** —— 验收：≥8 项且能分层——指令层（system prompt / AGENTS.md）、能力层（工具 / MCP）、上下文层（压缩 / repo map）、执行层（沙箱 / hooks）、质量层（测试 / 评审）。
4. **对照反思** —— 多数人的答案是最薄弱的两个是"**验证**"（没有 gate，Agent 说完成就完成）和"**权限**"（没有 deny-first）。

### 9.2 十二大模块解剖

1. **凭记忆画十二模块** —— 验收：12 个模块齐全，且每个标出"输入什么、输出什么"。
2. **`classify_error()`** —— 要点：四类——**可重试**（网络/限流）、**可修正**（参数错，回灌给模型）、**需升级**（权限/未知，转人工）、**致命**（预算耗尽，终止）。
3. **批量调度器** —— 要点：只读工具并发（线程池），写工具串行（锁/队列），`run_tests` 与 `write_file` 互斥。
4. **对照分析** —— 验收：给出判断依据（prompt 是否分层、deny 是否优先、是否有验证门）。

### 9.3 上下文工程与压缩

1. **`SummarizationMiddleware`** —— 验收：能看到触发点，摘要保留了关键决策而非流水账。
2. **`ObservationMaskingMiddleware`** —— 要点：屏蔽旧工具输出、保留最近 N 条，对比 token 与成功率（通常 token 大降、成功率基本持平）。
3. **JIT 检索版阅读 Agent** —— 要点：只给 `glob` / `grep` / 区间 `read`，禁止整文件读入；实测 token 降幅常在 50% 以上。
4. **上下文预算看板** —— 要点：横轴上下文规模、纵轴成功率，找拐点（一般在窗口占用 30–50% 之后开始下滑）。

### 9.4 权限护栏与沙箱

1. **`PIIMiddleware`** —— 验收：邮箱/手机号被 redact。
2. **`send_email` 必须审批** —— 要点：`interrupt` → 用户拒绝 → Agent 收到"被拒绝"的结果并**收尾**，而不是崩溃。
3. **`DockerSandbox`** —— 验收：三项限制各触发一次真实报错（越界被拒）。
4. **PreToolUse 装饰器** —— 要点：命中规则则格式化或拒绝，并写审计日志（谁、何时、拦了什么）。

### 9.5 验证循环

1. **三层验证矩阵** —— 要点：快速层（语法/lint，秒级）、阶段层（单测，分钟）、终局层（集成/e2e，十分钟）；失败分别走重试/回退/终止。
2. **`StopHook`** —— 验收：连续 block 8 次后强制终止，且能看到"block → 修复 → 通过"的完整链路。
3. **对抗性评审** —— 结论通常：只看 diff 的 Evaluator **更挑剔**，因为没有解释可以依赖，能发现"解释掩盖的问题"。
4. **四段式规则** —— 验收：规则可被 linter 执行，含 ERROR/WHY/FIX/EXAMPLE。

### 9.6 子 Agent 编排与长时任务

1. **50 个文件补测试** —— 要点：Worktree/Fork 按**文件分片**避免冲突，进度写文件，最后汇总；子 Agent 数量按"文件数 / 单上下文可处理量"定。
2. **`ProgressStore`** —— 验收：新会话读进度文件后能接上，跨 3 个上下文窗口不断档。
3. **嵌套子图 vs 单体** —— 要点：子图版主上下文 token **峰值低**，但总 token 可能更高（重复读取）；质量看结论是否更聚焦。
4. **Ralph Loop 的安全阀** —— 要点：连续 N 轮无进展 / 同一错误重复出现 / 预算超限 / 遇到高风险动作 → 停止强制继续，转人工。

### 9.7 Harness 工程方法论

1. **Fowler 2×2 矩阵** —— 验收：确定性/非确定性 × 单步/多步，四格各填 ≥2 个工具或产物。
2. **七个关键决策** —— 验收：入口形态、权限边界、上下文策略、验证方式、交付方式、可观测性、成本上限，逐条给出选择与理由。
3. **写 `AGENTS.md`** —— 验收：≤50 行，只写"代码里读不到"的信息（如"提交前必须跑 `make check`"）。
4. **规则的保质期** —— 要点：换更强模型后可以退役的规则，本质是"**补偿弱模型**"的临时手段，应标注到期条件。

### 9.8 构建最小可行 Harness

1. **跑通并破坏** —— 验收：`max_turns=3` 后终止原因变为 `max_turns`，trace 报告同步变化。
2. **加 `git_diff` 工具** —— 验收：schema 补齐、进 `READ_ONLY_TOOLS`、自检多一条断言且全绿。
3. **按 token 阈值压缩** —— 要点：按累计 token 估算动态截断，而不是固定"保留 6 条"；自检里对比压缩前后 token。
4. **接入真实评测** —— 要点：`judge_success` 必须**程序化判定**（测试是否通过、文件是否生成），不要用 LLM judge 当唯一标准。

### 9.9 开源 Harness 全景

1. **三分类** —— Harness（自带循环与工具，开箱即用）/ 底层编排库（给你积木，自己搭）/ 低代码平台（拖拽）。
2. **跑通 `dsh` 或 Deep Agents** —— 验收：能跑最小示例，记录安装坑（依赖、认证、平台差异）。
3. **权限矩阵** —— 验收：写清可读写目录、能否执行命令、能否联网，据此选沙箱方案。
4. **横向对比** —— 验收：5 个真实 backlog 任务 × 2 个 harness 的对比表 + 选型结论。

### 9.10 标准与 Skills

1. **50 行 `AGENTS.md`** —— 验收：只保留不可推断信息，并说明每条理由。
2. **`SKILL.md`** —— 要点：`description` 是**触发条件**，决定它何时被加载（渐进式披露）。
3. **Spec → pytest** —— 验收：验收标准能一一对应到测试用例。
4. **可移植性盘点** —— 要点：标出"迁移会丢"的项（如工具内嵌逻辑），给出上移到可移植层的方案。

### 9.11 评测与可观测性

1. **6 个指标** —— 完成率 / 平均轮数 / token 成本 / 工具错误率 / 验证通过率 / 人工介入率；每个都要写"退化时的可能原因"。
2. **接入 `AgentTracer`** —— 验收：3 个任务跑出 `summary()`，能指出最慢一步是谁。
3. **A/B `max_turns`** —— 结论：**不是越多越好**，超过必要轮数只增成本；要找拐点。
4. **失败模式归因** —— 验收：10 次里失败案例能归类到五类失败模式，并给占比最高那类的改造方案。

### 9.12 开源 Harness 源码解剖

1. **OpenHands 分层图** —— 要点：决策层（Agent/LLM）与执行层（Docker Runtime）解耦；好处：执行环境可替换、行为可审计与回放。
2. **设计 ACI** —— 验收：4–6 个命令，每个都能对应 SWE-agent 的一条原则（如结构化反馈、状态可见）。
3. **repo map vs 摘要压缩** —— repo map 适合**大仓库导航**（省 token 又保留结构），摘要适合**长对话**；用错会丢结构（该看的地方没进上下文）或丢细节。
4. **repo map 注入** —— 验收：19 项自检仍全绿，且记录压缩前后 token 变化。
5. **Code Agent 为什么必须沙箱** —— 动作能力边界不同：Code Agent 能执行**任意代码**（不可逆、可外泄），diff 编辑作用域受限（只能改指定文件），风险可控。

### 9.13 实战清单与模板

1. **清单自评** —— 验收：通过率 + 按 ROI 排序的三步改造计划。
2. **成熟度定位** —— 验收：定级（L0–L4）+ 落地该级"下一步"的一件事。
3. **反模式排查** —— 验收：3 条踩中的反模式，各对应到**具体代码行或配置文件**。
4. **`AGENTS.md` + `StopGate`** —— 验收：故意让测试失败一次，StopGate 确实拦住。
