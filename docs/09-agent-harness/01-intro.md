# 9.1 什么是 Agent Harness —— 从「模型能力」到「驾驭工程」

## 📖 导读

> **同一个模型，换个 Harness，任务完成率可以从 52.8% 涨到 66.5%，排名可以从 30 名开外冲进前 5。**

前面八部分，我们学会了用 LangChain / LangGraph 把模型、工具、记忆、RAG 组装起来。但到了 2026 年，社区达成了一个共识：

> **Agent = Model + Harness**

模型负责"推理"，而**模型之外的一切**——系统提示词、工具、技能、沙箱、编排循环、中间件、权限、验证——统称为 **Harness（驾驭层 / 智能体框架）**。当模型不再是瓶颈，**Harness 就成了决定性的战场**。

本部分（第九部分）是整个教程的**收官之作**，将带你从"会搭 Agent"进阶到"会设计 Harness"，这正是 2026 年 AI 工程化最核心的能力。

---

## 一、核心公式：Agent = Model + Harness

### 1.1 一句话定义

LangChain 的 Vivek Trivedy 给出了最锋利的定义：

> **"If you're not the model, you're the harness."**
> （如果你不是模型，那你就是 harness。）

也就是说，**Harness = 模型之外的代码、配置与执行逻辑的总和**，包括：

| 组成 | 具体内容 |
|------|----------|
| **指令层** | System Prompt、AGENTS.md / CLAUDE.md、Skills、Spec |
| **能力层** | 工具（Tools）、MCP Server、子 Agent |
| **上下文层** | 上下文组装、压缩、检索、渐进式披露 |
| **状态层** | 会话记忆、长期记忆、Checkpoint、进度文件 |
| **执行层** | 沙箱、权限、Hooks、超时与并发控制 |
| **质量层** | 验证循环、护栏、人工审批 |
| **运维层** | 生命周期、健康检查、可观测性、成本预算 |

### 1.2 一个关键区分

| 概念 | 是什么 |
|------|--------|
| **Agent** | 一种**涌现出的行为**——有目标、会用工具、能自我纠正 |
| **Harness** | 产生这种行为的**机器** |
| **Model** | Harness 内部一个**可替换的组件** |

所以当有人说"我做了一个 Agent"时，更准确的说法是：**"我做了一个 Harness，并把它指向了某个模型。"**

> 💡 **同一个 Claude 模型**，分别驱动聊天界面、Claude Code（终端编码 Agent）、企业 API 集成——**权重完全相同，行为截然不同**，差别全部来自 Harness。

## 二、三个经典类比

理解 Harness，最好的方式是记住三个类比。

### 2.1 马具（Horse Tack）

**Harness** 这个词本意就是"马具"。

```
LLM 是一匹强壮的马：
  ✅ 力量巨大（推理能力）
  ✅ 跑得飞快（生成速度）
  ❌ 没有方向感
  ❌ 没有边界意识
  ❌ 没有"停止"的概念

Harness 就是辔头、缰绳与马鞍：
  ✅ 决定往哪走（目标）
  ✅ 决定能走多快（预算）
  ✅ 决定什么时候停（终止条件）
```

### 2.2 操作系统（Operating System）

Hugging Face 的 Phil Schmid 给出了最广为流传的类比：

| 计算机 | Agent 系统 |
|--------|-----------|
| **CPU** | 模型（Model）—— 执行指令、做计算 |
| **内存 / RAM** | 上下文窗口（Context Window）—— 瞬时寻址空间 |
| **硬盘** | 外部存储 / 向量库 —— 持久化 |
| **设备驱动** | 工具集成（Tools / MCP） |
| **操作系统** | **Harness** —— 资源调度、内存管理、权限、进程、崩溃恢复 |

> 🔥 金句：**"没有 OS 的 CPU 是加热元件；没有 Harness 的模型是 Demo。"**

这个类比的深刻之处在于：**CPU 的性能提升不会让操作系统消失**。同理，模型再强，Harness 也不会消失——因为总要有人管理上下文窗口、执行工具调用、持久化状态、验证结果。

### 2.3 脚手架（Scaffolding）

工地脚手架是**临时基础设施**：它不参与建造，但没有它工人够不着高层。

关键洞察：**大楼盖好，脚手架就拆了。**

> 📌 模型变强，Harness 的复杂度应当**下降**。
> Manus 在六个月内重写架构 **5 次**，每一次都在**去复杂度**：从复杂工具定义 → 通用 shell 执行；从"管理 Agent" → 简单结构化 handoff。

## 三、为什么 2026 是「Harness 之年」

### 3.1 硬数据：模型没变，只改 Harness

| 实验 | 结果 |
|------|------|
| **LangChain TerminalBench 2.0** | 同一模型、同一权重，**只更换包裹 LLM 的基础设施层**，排名从 **30 名开外 → 第 5 名** |
| **LangChain（GPT-4）** | 只改 harness 不换模型，任务完成率 **52.8% → 66.5%** |
| **Meta-Harness 论文** | 让模型自动优化 harness，比 ACE 高 **7.7pp**，上下文 token 减 **4×** |
| **Token 效率实验** | 同一模型同一 API，不同 Harness 完成同一任务的 token 消耗**相差约 70 倍** |
| **Vercel v0** | 构建编码 Agent 时**移除 80% 的工具**，结果反而更好 |

### 3.2 可靠性的数学：为什么"95% 可用"仍然会失败

这是理解 Harness 价值最直观的一张表：

```
单步成功率 95%，串联 20 步：
  0.95^20 ≈ 36%          ← 端到端完成率只有三分之一！

单步成功率 99%，串联 10 步：
  0.99^10 ≈ 90.4%        ← 错误复合依然很快
```

**结论**：单步可靠性再高，长任务也会因为**错误复合（error compounding）**而崩塌。Harness 的核心价值，就是在每一步之间**加入验证与恢复**，把复合误差压回去。

### 3.3 代码的现实：Agent 里"模型决策"只占极小部分

Claude Code 团队的统计（被广泛引用）：

```
Claude Code 代码库构成：
  ██ 1.6%   模型决策逻辑（while 循环 + 决策）
  ████████████████████████████████████████ 98.4%  Operational Harness
                                                  （权限系统、五层上下文压缩、
                                                    工具路由、安全护栏、生命周期钩子）
```

Anthropic 自己把 runtime 称作 **"dumb loop"**（笨循环）——**所有智能在模型里，Harness 只负责管理每一轮（turn）**。

> 🎯 这解释了为什么"照抄一个 Agent Demo"很容易，做出**生产级 Agent** 却极难：难点 98.4% 都在 Harness 里。

### 3.4 竞争格局的转移

| 时间 | 竞争焦点 |
|------|----------|
| 2023 | 谁有更好的 Prompt |
| 2024–2025 | 谁有更好的 Context 工程 / 框架 |
| **2026** | **谁的 Harness 更好** |

> 🔥 行业格言：**"The model is commodity. The harness is moat."**
> （模型是商品，Harness 是护城河。）

**时间预期警告**：生产级 Harness 需要**数月而非数天**。Manus 花了 6 个月 + 5 次重写；LangChain 为 LangGraph 执行引擎迭代了 **4 种架构、耗时超一年**；Martin Fowler 团队记录：**Harness 的工程量常常大于 Agent 逻辑本身**。

## 四、三层工程同心圆

AI 工程能力可以画成三个层层包含的同心圆：

```
        ┌─────────────────────────────────────────┐
        │  ③ Harness Engineering（驾驭工程）        │
        │  ┌───────────────────────────────────┐  │
        │  │  ② Context Engineering（上下文工程）│  │
        │  │  ┌─────────────────────────────┐  │  │
        │  │  │  ① Prompt Engineering        │  │  │
        │  │  │  （设计模型收到的指令）        │  │  │
        │  │  └─────────────────────────────┘  │  │
        │  │  管理"模型何时看到什么"             │  │
        │  └───────────────────────────────────┘  │
        │  上面两层 + 工具编排、状态持久化、错误恢复、  │
        │  验证循环、安全执行、生命周期管理            │
        └─────────────────────────────────────────┘
```

| 层级 | 关注点 | 关键问题 |
|------|--------|----------|
| ① Prompt Engineering | 指令措辞 | "怎么问，模型才答得好？" |
| ② Context Engineering | 信息选择与压缩 | "这一步该让模型看到什么？" |
| ③ **Harness Engineering** | 系统机制 | "**怎么用机制保证质量，而不是靠请求模型自觉？**" |

> 🔑 Harness Engineering 的核心主张：
> **用机制强制质量，而不是用 prompt 请求质量。**
>
> 一条 linter 规则加进去，**从此以后每一个会话都不会再犯这个错**——Prompt 是一次性的，Harness 是**永久复利**的。

## 五、Harness vs Framework：不是一回事

初学者最容易混淆的一点：**"框架（Framework）"和"Harness"不是同义词。**

| 维度 | Framework（LangGraph 等） | Harness（Claude Code 等） |
|------|---------------------------|---------------------------|
| **决策者** | 图结构定义路径，模型填充节点 | **模型全权决策**，Harness 只管执行环境 |
| **出现阶段** | 构建期（Build-time） | **运行期（Run-time）** |
| **关注点** | 组装架构、编排节点 | 治理行为、约束执行 |
| **主要使用者** | 开发者 | 基础设施 / 平台团队 |
| **灵活性** | 有限（边决定可能路径） | 高（模型自由） |
| **可预测性** | 高 | 较低 |
| **开发成本** | 高（需设计图结构） | 低（只配环境） |
| **对模型要求** | 低 | 高 |
| **适用场景** | 步骤固定的 workflow | 开放式 Agent 任务 |

> ⚖️ **平衡观点**：对 CI/CD、数据 ETL 等**步骤固定**的流水线，静态 workflow（Framework）更合适、更可控；对开放式任务（编码、研究、运维），Harness 更能释放模型能力。
>
> Anthropic 在 re:Invent 2025 的建议是：**"团队应避免过度隐藏底层机制的强主张框架。"**

### 5.1 两者其实是互补的

```text
你的 Agent 系统
├── 【Framework 层】LangGraph 定义"骨架"：状态、节点、条件边、持久化
│   └── 负责：确定性的流程控制
└── 【Harness 层】包裹模型的一切：提示词组装、工具、权限、压缩、验证
    └── 负责：每个 turn 的执行环境与治理
```

**本教程前八部分教你用好 Framework；第九部分教你设计 Harness。**

## 六、Harness 解决的五类失败模式

Harness 不是抽象概念，它直接对应五类最常见的生产事故：

| 失败模式 | 症状 | Harness 的修复手段 |
|----------|------|-------------------|
| **上下文腐化**（Context Rot） | 重解已完成的问题、自相矛盾、丢失原目标 | 压缩、剪枝、进度文件、子 Agent 隔离 |
| **工具爆炸**（Tool Explosion） | 选错工具、生成畸形调用 | 按任务阶段**动态收窄**工具集 |
| **静默失败**（Silent Failure） | 工具报错却当成成功继续（**最危险**） | 每次工具调用后做结构化输出校验 |
| **无限循环**（Infinite Loop） | 同一个错误反复重试 | 最大重试次数 + 指数退避 + 启发式循环检测 |
| **状态损坏**（State Corruption） | 恢复后外部世界已变，前置条件不成立 | 恢复时**校验前置条件**，而非盲目重放 |

> 📌 第九部分后续章节会逐一给出这五类问题的工程解法。

## 八、本章总结

| 知识点 | 一句话说明 |
|--------|------------|
| **核心公式** | **Agent = Model + Harness**，模型之外的一切都是 Harness |
| **三大类比** | 马具（方向与约束）、操作系统（资源与调度）、脚手架（会随模型变强而变薄） |
| **2026 关键数据** | 只改 Harness：TerminalBench 排名 30+ → 第 5；完成率 52.8% → 66.5% |
| **可靠性数学** | 95% 单步 × 20 步 ≈ 36%，必须靠 Harness 抑制错误复合 |
| **代码现实** | Claude Code 中模型决策仅占 1.6%，98.4% 是 Harness |
| **三层同心圆** | Prompt ⊂ Context ⊂ **Harness** Engineering |
| **方法论核心** | **用机制强制质量，而非用 prompt 请求质量** |
| **vs Framework** | Framework 管构建期编排，Harness 管运行期治理，两者互补 |
