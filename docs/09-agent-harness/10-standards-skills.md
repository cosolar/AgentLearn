## 一、问题的起点：配置文件的碎片化

2024–2025 年，每个 coding agent 都想要一份"自己的"常驻指令文件：

```text
没有统一标准的世界：
  CLAUDE.md                    ← Claude Code
  .cursorrules / .cursor/rules ← Cursor
  GEMINI.md                    ← Gemini CLI
  copilot-instructions.md      ← GitHub Copilot
  .windsurfrules               ← Windsurf
  ...
  （同一份"项目约定"，被你抄了 N 遍，且每份都在悄悄漂移）
```

| 配置文件 | 归属工具 | 可移植性 |
|---------|---------|---------|
| `CLAUDE.md` | Claude Code | ❌ 仅 Claude Code 读取 |
| `.cursorrules` / `.cursor/rules` | Cursor | ❌ 仅 Cursor 读取 |
| `GEMINI.md` | Gemini CLI | ❌ 仅 Gemini CLI 读取 |
| `copilot-instructions.md` | GitHub Copilot | ❌ 仅 Copilot 读取 |
| **`AGENTS.md`** | **跨工具标准** | ✅ **30+ 工具读取** |

**碎片化的代价**：

- **维护成本**：同一份构建命令、代码风格写在 5 个文件里，改一处忘四处
- **认知负担**：新人不知道"该信哪个文件"
- **迁移失效**：在 Claude Code 精心调好的 harness，切到 Cursor / Codex **几乎全部失效**（这正是本章要解决的核心问题，见第五节）

> 🎯 **一句话**：`AGENTS.md` 相当于 **"除 Claude Code 之外所有 coding agent 的 CLAUDE.md"**——或者说，是那个本该一开始就存在的**统一约定文件**。

## 二、AGENTS.md 标准

### 2.1 起源与托管

| 项目 | 说明 |
|------|------|
| **推出方** | **OpenAI**，**2025 年 8 月**推出 |
| **当前托管方** | **Linux 基金会下的 Agentic AI 基金会** |
| **形态** | 跨工具的 **Markdown 常驻指令文件** |
| **生态规模** | **30+ 工具**支持、**6 万+ 仓库**使用 |
| **核心价值** | 一份约定，处处生效 |

**它解决的问题**：配置文件一度碎成一地（`CLAUDE.md`、`.cursorrules`、`GEMINI.md`、`copilot-instructions.md`……）。AGENTS.md 用一个**厂商中立**的 Markdown 文件，把所有 agent 都需要的"项目常识"集中起来。

**与 `CLAUDE.md` 的关系**：

```text
CLAUDE.md  ──▶  Claude Code 专属
AGENTS.md  ──▶  跨工具通用（Claude Code 亦可读取/兼容）
              ≈ "除 Claude Code 外所有 coding agent 的 CLAUDE.md"
```

> 💡 实践上，很多团队同时保留两者：`AGENTS.md` 放**通用约定**，`CLAUDE.md` 放 **Claude Code 专属**（如果有的话）。

### 2.2 级联加载机制与 32 KiB 上限

**Codex 的级联加载**：Codex 会从当前工作目录**逐级向上**查找 `AGENTS.md`，把沿途找到的文件都纳入上下文，从而实现"仓库级 + 目录级"的分层指令。

```text
/repo/AGENTS.md                 ← 仓库根：全局约定
/repo/packages/api/AGENTS.md    ← 子包：该包的专属约定
/repo/packages/api/auth/AGENTS.md ← 更深目录：更细的覆盖

当前工作目录在 /repo/packages/api/auth 时：
  逐级向上加载 → auth + api + 根，后加载者优先（或按实现规则合并）
```

| 机制 | 说明 |
|------|------|
| **级联查找** | 从 cwd 向上逐级查找 `AGENTS.md` |
| **就近优先** | 越靠近当前目录的文件，越能覆盖上层约定 |
| **32 KiB 上限** | 加载内容有总量限制（**以官方文档为准**），防止上下文被撑爆 |
| **超出即截断** | 超限通常会被截断，因此要**精炼**（见 2.4） |

**优先级栈**（从高到低）：

```text
优先级高
  ▲
  │  1. 服务端 system message        ← 厂商固定，用户不可改
  │  2. 工具定义（tool definitions）  ← harness 注入
  │  3. 开发者指令（developer msg）    ← 应用层注入
  │  4. 用户指令 / AGENTS.md          ← 你的项目约定在这里
  │  5. 对话历史                      ← 越低越"软"
  ▼
优先级低
```

> 🎯 **关键推论**：`AGENTS.md` 处于优先级栈的**中段**——它能覆盖对话历史，但**无法覆盖**服务端 system message 与工具定义。所以：
> - 不要试图用 AGENTS.md **对抗** harness 的内置行为
> - 要**顺应**它：AGENTS.md 只补充"模型无法从代码推断"的项目常识

### 2.3 可复制的 AGENTS.md 模板

以下模板可直接放进仓库根目录，按需删改。**控制在 50 行以内**（见 2.4）。

```markdown
# AGENTS.md

## 项目概览
- 本项目是 XXX（一句话说明是什么、给谁用）
- 技术栈：Python 3.12 · LangChain v1 · LangGraph 1.1
- 主力模型：gpt-5.5

## 构建与测试命令
```

# 安装依赖
uv sync

# 运行测试
uv run pytest -q

# 单个测试文件
uv run pytest tests/test_api.py -q

# 代码检查
uv run ruff check .
```

## 代码风格
- 使用 `ruff` 格式化 + 检查，行宽 100
- 类型注解必须完整；公共函数必须有 docstring
- 禁止使用 `print` 调试，改用 `logging`

## 目录结构导航
- `src/`        —— 核心库代码
- `tests/`      —— 测试（与 src 结构对应）
- `docs/`       —— 文档（Markdown，中文）
- `examples/`   —— 可运行示例

## 禁止事项
- 不要修改 `uv.lock`（除非明确要求升级依赖）
- 不要提交 `.env`、密钥、token
- 不要在没有测试的情况下改动 `src/core/` 的公共 API
- 不要 `--force` 推送或改写已推送的历史

## PR 惯例
- 分支命名：`feat/xxx`、`fix/xxx`
- Commit：Conventional Commits（`feat:`、`fix:`、`docs:`）
- PR 描述需包含：变更动机、验证方式、影响范围
- 每个 PR 只做一件事；测试必须通过
```

**为什么这样写？** 对照优先级栈——这些内容**全都是"模型读代码也猜不出来"的**：构建命令、风格约定、禁止事项、PR 惯例。

### 2.4 维护实践

| 实践 | 说明 |
|------|------|
| **控制在 50 行以内** | 越长越容易被截断、越容易被忽略 |
| **只放"推断不出的东西"** | 能从代码看出来的（如"这是个 Python 项目"）不要写 |
| **"地图而非手册"** | 告诉 Agent **去哪里找**，而不是把内容全抄进来 |
| **全大写警告关键字** | `IMPORTANT`、`NEVER`、`MUST` 提升注意力（有研究支持，具体效果以实践为准） |
| **大型仓库用级联** | 根 `AGENTS.md` 放全局约定，目录级 `AGENTS.md` 放局部覆盖 |
| **定期清理** | 每条规则都问：删掉会怎样？不会怎样就删掉 |
| **当作代码维护** | 纳入 PR 评审，避免"文档腐烂" |

**"地图而非手册"示例**：

```markdown
❌ 手册式（把内容抄进来，占满上下文）：
   以下是完整的 API 设计规范：1. ... 2. ... 3. ...（200 行）

✅ 地图式（指向来源）：
   API 设计规范见 docs/api-guidelines.md，改 API 前必读。
```

## 三、Agent Skills

### 3.1 定义与按需加载

**Agent Skill** 是**可复用的能力包**，典型形态：

```text
my-skill/
├── SKILL.md          # 技能说明（元数据 + 指令 + 何时使用）
├── scripts/          # 可执行脚本
│   └── run.py
├── resources/        # 模板、数据、参考文档
│   └── template.md
└── ...
```

核心机制是 **渐进式披露（progressive disclosure）**：

```text
第 1 层（常驻）：只加载 SKILL.md 的 metadata（name + description）
                 → 让 agent 知道"有这么个技能，什么时候该用"
                          ↓ 命中触发条件
第 2 层（按需）：加载 SKILL.md 正文（流程、注意事项）
                          ↓ 需要具体资源时
第 3 层（更深）：加载 scripts / resources 中的文件
```

> 🎯 **价值**：**能力可以无限扩展，上下文只按需付费**。你有 100 个技能，不代表每轮对话都塞 100 份说明——只有真正用到的那 1 个会被完整展开。

### 3.2 为什么成为 2026 年下半年最热门的开源叙事

| 原因 | 说明 |
|------|------|
| **解决了"上下文经济"难题** | 技能再多，常驻成本只有 metadata |
| **可复用、可分享** | 一个技能包，跨项目、跨 harness 复用 |
| **门槛低** | 一个目录 + 一份 Markdown 就能写 |
| **GitHub Trending 现象** | 大量 skill 仓库冲上 Trending，形成"技能市场" |
| **跨 harness 通用性诉求** | Skills 被视为比"厂商私有配置"更中立的能力载体 |

### 3.3 Skill 与 Tool 的区别

| 维度 | **Tool** | **Skill** |
|------|---------|-----------|
| **本质** | 一个函数（输入 → 输出） | 一套**流程 + 知识 + 资源** |
| **形态** | `@tool` 装饰器 / MCP 工具 | 目录（`SKILL.md` + 脚本 + 资源） |
| **加载** | 常驻在工具列表 | **按需**（渐进式披露） |
| **内容** | 单一动作 | 多步骤方法论、注意事项、模板 |
| **类比** | "给你一把螺丝刀" | "给你一本装配手册 + 工具 + 零件" |
| **典型例子** | `read_file`、`web_search` | "生成周报"、"迁移数据库"、"发版流程" |

> 💡 一句话：**Tool 是"函数"，Skill 是"带流程与知识的技能包"**。Skill 内部可以调用多个 Tool。

### 3.4 Spec / Rule / Skill 三层区分

三者容易混淆，真正的区别在于**加载机制**：

```text
┌─────────────────────────────────────────────────────────────┐
│  Rule（规则）—— 头部常驻                                      │
│  如 AGENTS.md / 系统规则                                     │
│  始终在上下文里；要求"每次都遵守"                              │
├─────────────────────────────────────────────────────────────┤
│  Skill（技能）—— 尾部按需                                    │
│  仅 metadata 常驻；命中触发条件才展开正文                      │
│  要求"在特定任务时才需要知道的知识/流程"                        │
├─────────────────────────────────────────────────────────────┤
│  Spec（规格）—— 被 Skill 消费                                │
│  描述"要做成什么样"；由 Skill 或流程读取作为依据                │
│  既当前馈（照着做），也当反馈（拿来验收）                       │
└─────────────────────────────────────────────────────────────┘
```

| 类型 | 加载机制 | 回答的问题 | 典型载体 |
|------|---------|-----------|---------|
| **Rule** | **头部常驻** | "任何时候都要遵守什么？" | `AGENTS.md`、系统规则 |
| **Skill** | **尾部按需** | "这类任务该怎么做？" | `SKILL.md` + 脚本/资源 |
| **Spec** | **被 Skill 消费** | "做成什么样才算对？" | 规格文档（如 OpenSpec 产物） |

> 🎯 **记忆口诀**：**Rule 常驻头顶、Skill 按需到手、Spec 拿来对标。**

### 3.5 一个完整的 Skill 示例

**场景**：给项目加一个"发版检查"技能。

**目录结构**：

```text
.claude/skills/release-check/        # 目录名因 harness 而异，以官方文档为准
├── SKILL.md
├── scripts/
│   └── check_version.py
└── resources/
    └── release-checklist.md
```

**`SKILL.md` 内容**：

```markdown
---
name: release-check
description: 在发布新版本前执行完整的发版前检查（版本号、CHANGELOG、测试、迁移脚本、文档）。当用户提到"发版""release""打 tag""上线前检查"时使用。
---

# 发版检查

## 何时使用
当用户要求发布新版本、打 tag、或做上线前检查时。

## 步骤

1. **确认版本号**
   运行 `python scripts/check_version.py`，确认 `pyproject.toml`
   中的版本号符合语义化版本，且高于上一个 tag。

2. **更新 CHANGELOG**
   参考 `resources/release-checklist.md` 的格式，为本次改动
   补全 CHANGELOG 段落（Added / Changed / Fixed）。

3. **跑全量测试**
   ```bash
   uv run pytest -q
   ```
   任一失败则**停止**，先修复再继续。

4. **检查迁移脚本**
   若有数据库/schema 变更，确认迁移脚本存在且可回滚。

5. **更新文档**
   确认 `docs/` 中受影响页面已同步。

6. **输出检查报告**
   汇总以上各项的通过/失败，列出阻塞项。

## 注意事项
- 任一步骤失败，**不要**继续后续步骤
- 不要自行推送 tag，交由用户确认后再推送
- 报告使用中文
```

**它何时被加载？**

```text
用户："帮我发 1.3.0 版本"
        │
        ▼
[第1层] harness 只看到 metadata：
        "release-check —— 发版前检查……提到发版时使用"
        → 命中触发条件
        ▼
[第2层] 加载 SKILL.md 正文（6 个步骤）
        ▼
[第3层] 步骤执行时按需读取 scripts/ 与 resources/
```

**与其他层的关系**：

| 层 | 本示例中的角色 |
|----|--------------|
| **Rule（AGENTS.md）** | 规定"不要 `--force` 推送""提交规范"等常驻约束 |
| **Skill** | `release-check`，仅发版时展开 |
| **Tool** | `read_file`、`run_command`、`git` 等，被 Skill 的步骤调用 |
| **Spec** | 若项目有发布规格文档，则作为"验收依据" |

### 3.6 技能市场与生态

| 生态要素 | 说明 |
|---------|------|
| **awesome 列表** | 社区维护的 skill 精选仓库 |
| **GitHub Trending** | Skill 仓库频繁上榜，形成"技能市场"氛围 |
| **跨 harness 复用问题** | ⚠️ 各 harness 的 skill 目录位置、metadata 字段**不完全一致**，需要适配层 |
| **质量参差** | 第三方 skill 可能含不安全脚本，**使用前审查** |
| **版本管理** | 建议固定版本，纳入代码评审 |

## 四、Spec 驱动开发（Spec-driven Development）

### 4.1 核心思想

> **先写"可执行规格"，再让 Agent 按规格实现与验证。**

传统流程：需求 → 人写代码 → 测试。
Spec 驱动流程：需求 → **写规格** → Agent 生成任务清单 → Agent 逐项实现 → **用规格验收** → 更新规格。

```text
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  写 Spec │───▶│ 生成任务  │───▶│ 逐项实现  │───▶│ 按 Spec  │
│（可执行）│    │  清单     │    │          │    │  验收     │
└──────────┘    └──────────┘    └──────────┘    └────┬─────┘
      ▲                                              │
      └──────────────── 更新 Spec ◀──────────────────┘
```

### 4.2 代表工具：OpenSpec 与 Spec Kit

| 工具 | 定位 | 状态 |
|------|------|------|
| **OpenSpec** | 开源规格驱动开发工具链 | **2026 年走向成熟** |
| **GitHub Spec Kit** | 官方风格的规格驱动工具集 | 与 OpenSpec 属同类思路（**具体差异以官方文档为准**） |

> ⚠️ 两个工具的边界、命令与产物格式都在快速演进，**以官方文档为准**。本节重点讲**方法论**而非某个工具的具体命令。

### 4.3 为什么 Spec 天然和 Harness 结合

因为规格文件同时充当 **guides（前馈）** 与 **sensors（反馈）** 的依据——这正是 Harness Engineering 的核心思维（见 [9.7 Harness Engineering](07-harness-engineering.md)）：

```text
              ┌──────────────────────┐
              │        Spec           │
              └───────┬──────┬───────┘
                      │      │
        作为 guides ───┘      └─── 作为 sensors
        （前馈：照着做）            （反馈：拿来验收）
                      │      │
                      ▼      ▼
              ┌──────────────────────┐
              │   Agent 实现 + 验证   │
              └──────────────────────┘
```

| 角色 | 含义 | Spec 的作用 |
|------|------|-----------|
| **guides（前馈）** | 事前告诉 Agent 该怎么做 | 规格描述目标行为，模型照此实现 |
| **sensors（反馈）** | 事后判断做对没有 | 规格转成验收测试，自动判定 |

> 🎯 **关键洞察**：**一份规格，两处复用**。它既是指南又当尺子，这是 Spec 驱动开发与"写个文档然后各干各的"最本质的区别。

### 4.4 一个 spec 驱动的工作流示例

**步骤 1：写 spec**

```markdown
# spec: 用户限流

## 目标
为公开 API 增加按用户限流，防止滥用。

## 行为规格
- 默认限额：每用户 100 请求 / 分钟
- 超限返回 HTTP 429，body 含 `retry_after` 秒数
- 限额可配置：环境变量 `RATE_LIMIT_PER_MINUTE`
- 计数窗口为滑动窗口（不是固定窗口）

## 验收标准
1. 第 101 次请求返回 429
2. `retry_after` 为正整数
3. 设置 `RATE_LIMIT_PER_MINUTE=10` 时，第 11 次返回 429
4. 不同用户互不影响
```

**步骤 2：Agent 生成任务清单**

```text
[ ] 设计限流器接口（滑动窗口）
[ ] 实现内存后端
[ ] 接入中间件
[ ] 支持环境变量配置
[ ] 编写验收测试（对应 spec 的 4 条标准）
[ ] 更新文档
```

**步骤 3：逐项实现**（Agent 循环执行，必要时读 AGENTS.md 的规则与 skill 的流程）

**步骤 4：用 spec 做验收测试**

```python
# tests/test_rate_limit.py —— 直接把 spec 的验收标准变成测试
def test_101st_request_rejected(client):
    for _ in range(100):
        assert client.get("/api/ping").status_code == 200
    resp = client.get("/api/ping")
    assert resp.status_code == 429
    assert resp.json()["retry_after"] > 0

def test_configurable_limit(client, monkeypatch):
    monkeypatch.setenv("RATE_LIMIT_PER_MINUTE", "10")
    for _ in range(10):
        assert client.get("/api/ping").status_code == 200
    assert client.get("/api/ping").status_code == 429
```

**步骤 5：更新 spec**（若发现有遗漏的边界情况，补进 spec——**规格与实现同步演进**）

> 💡 **三方收益**：规格是给**人**看的共识、给 **Agent** 的指南、给 **CI** 的验收依据。

## 五、跨工具一致性的现实问题

### 5.1 现实：切换即失效

一个非常普遍、也非常痛的场景：

```text
在 Claude Code 上精心调好的 harness
   ├── CLAUDE.md（项目约定）
   ├── .claude/skills/（技能）
   └── 各种私有配置
              │
              │  某天团队决定改用 Cursor / Codex
              ▼
        💥 几乎全部失效
        （文件位置不对、格式不对、没人读）
```

**这正是 AGENTS.md / Skills 要解决的问题**：把"工具私有配置"尽量上移为"跨工具的开放标准"。

### 5.2 "最大化可移植性"的配置分层建议

**原则：把可移植的内容放标准文件，把不可移植的内容隔离在工具专属目录。**

```text
┌─────────────────────────────────────────────────────────────┐
│  ① 通用层（可移植）—— AGENTS.md                              │
│     项目概览 / 构建测试命令 / 代码风格 / 禁止事项 / PR 惯例    │
│     30+ 工具都会读 → 迁移不丢                                │
├─────────────────────────────────────────────────────────────┤
│  ② 能力层（半可移植）—— Skills                                │
│     方法论、流程、脚本；metadata 尽量贴近标准                 │
│     目录位置可能需按 harness 适配（软链接/生成）               │
├─────────────────────────────────────────────────────────────┤
│  ③ 规格层（可移植）—— Spec                                    │
│     用纯 Markdown 描述行为与验收标准，与工具无关              │
├─────────────────────────────────────────────────────────────┤
│  ④ 工具专属层（不可移植）—— 隔离                               │
│     CLAUDE.md / .cursor/rules / 私有 prompt / 权限配置        │
│     只放"本工具独有"的东西，迁移时明确放弃                     │
└─────────────────────────────────────────────────────────────┘
```

**配置分层对照表**：

| 内容 | 放哪里 | 可移植性 | 迁移时 |
|------|-------|---------|--------|
| 项目概览、技术栈 | `AGENTS.md` | ✅ 高 | 直接带走 |
| 构建/测试命令 | `AGENTS.md` | ✅ 高 | 直接带走 |
| 代码风格、禁止事项 | `AGENTS.md` | ✅ 高 | 直接带走 |
| PR / commit 惯例 | `AGENTS.md` | ✅ 高 | 直接带走 |
| 能力流程（发版、迁移） | **Skill**（`SKILL.md`） | 🟡 中 | 调整目录/字段 |
| 行为规格与验收 | **Spec**（Markdown） | ✅ 高 | 直接带走 |
| Claude Code 专属配置 | `CLAUDE.md` / `.claude/` | ❌ 低 | 放弃/重写 |
| Cursor 专属规则 | `.cursor/rules` | ❌ 低 | 放弃/重写 |
| 工具权限/沙箱设置 | 各工具配置文件 | ❌ 低 | 需重新配置 |

> 🎯 **实践建议**：
> 1. **单一事实来源**：通用约定只在 `AGENTS.md` 写一遍
> 2. **生成优于复制**：若某工具需要别的格式，用脚本生成，而非手抄
> 3. **隔离私有配置**：把不可移植项集中到工具专属目录，迁移时心里有数
> 4. **定期做"迁移演练"**：假设明天换工具，哪些会丢？丢的先想办法上移

## 📝 课后练习

1. **起草题**：为你的项目写一份 **50 行以内**的 `AGENTS.md`，只保留"模型无法从代码推断"的内容，并说明每条的理由
