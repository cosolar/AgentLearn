# 5.6 RAG 评估 —— 用数据证明检索与回答的质量

> 📅 更新至 2026-10 · 技术栈基线见 [教程大纲](../教程大纲.md)

## 📖 导读

前五节我们把 RAG 搭了起来、也做了优化。但一个绕不开的问题是：**你怎么知道它变好了？**

> 💡 **一句话结论**：RAG 的"好"必须被**量化**——用一组固定的「黄金集」，把检索与生成的质量变成可比较、可回归的数字。凭感觉调的优化，大概率是自我安慰。

**前置阅读**：[5.1 RAG 原理](./01-RAG原理.md)、[5.4 优化策略](./04-优化策略.md)、[6.2 评估与优化](../06-高级主题/02-评估与优化.md)。

**本章你将学到**：
1. 为什么"跑起来能答"不等于"质量可接受"
2. 检索侧与生成侧两类指标，以及哪些**可以程序化判定**
3. 如何设计一份不自我欺骗的**黄金集（Golden Set）**
4. 跑通配套评测脚本 [`examples/05-rag-kb/eval.py`](../../examples/05-rag-kb/eval.py)
5. 把评估接进 CI，让"变差"在合并前就被拦住

## 一、为什么必须评估

RAG 有个隐蔽的陷阱：**它几乎总能给出一个"看起来合理"的答案**。

| 现象 | 真实原因 | 凭感觉的结论 |
|------|---------|-------------|
| 回答流畅、有来源标注 | 检索命中但**内容不相关** | "效果不错" |
| 回答正确 | 模型**用自己的知识**答的，没用到检索 | "RAG 起作用了" |
| 回答错误 | 检索**没召回**关键段落 | "模型不行" |

三个现象里有两个会骗过肉眼。**只有量化，才能区分"检索失败"和"生成失败"**——而这两者的修法完全不同（前者调检索/切分，后者调提示词/模型）。

> 🔗 这与 [6.2 评估与优化](../06-高级主题/02-评估与优化.md) 的核心主张一致：**程序化判定优先，LLM-judge 只作补充**。

---

## 二、两类指标：检索侧 vs 生成侧

RAG 是"检索 → 生成"两段式，评估也必须**分段**：

```text
问题 ──▶ [检索器] ──▶ 上下文 ──▶ [生成器] ──▶ 回答
           ▲                        ▲
      检索侧指标                生成侧指标
    （可程序化、可离线）      （部分需 LLM 判定）
```

| 侧 | 指标 | 判定方式 | 能离线算吗 |
|:---|:-----|:---------|:----------:|
| **检索侧** | Hit@k（命中率） | 期望来源是否在前 k 条 | ✅ |
| | MRR（平均倒数排名） | 首个正确结果的排名倒数均值 | ✅ |
| | Source Recall（来源召回） | 期望来源被覆盖的比例 | ✅ |
| | nDCG@k | 考虑排序位置的加权命中 | ✅ |
| | Context Precision | 检索结果里"有用"的占比 | 半程序化 |
| **生成侧** | Faithfulness（忠实度） | 回答是否忠于上下文 | ❌ 需 LLM |
| | Answer Relevance | 回答是否切题 | ❌ 需 LLM |
| | Answer Correctness | 与标准答案的一致性 | 半程序化（有标准答案时可程序化） |

> 🎯 **关键原则**：**能用程序判定的，绝不交给 LLM**。LLM-judge 有偏差、不可复现、还要花钱——它只该用在"确实无法程序化"的地方（如忠实度）。

## 三、黄金集（Golden Set）怎么设计

黄金集 = 一组**带标准答案的问题**。它的质量直接决定评估的可信度。

一条黄金样例通常包含：

| 字段 | 说明 | 示例 |
|:-----|:-----|:-----|
| `question` | 用户真实会问的问题 | "《数据合规政策》由谁制定？" |
| `sources` | 期望命中的**来源文件** | `["02-合规政策.md"]` |
| `keywords` | 期望出现在上下文里的**关键词** | `["法务部"]` |
| `answer`（可选） | 标准答案，用于算 Answer Correctness | "法务部" |

**设计黄金集的五条经验**：

1. **问题必须来自真实场景**——自己拍脑袋编的问题，评估的是"你会不会编题"，不是系统能力。
2. **覆盖三类**：单跳事实题、**多跳题**（跨文档）、**负样本**（语料里没有答案，看它会不会硬答）。
3. **每条都要有明确的"正确答案"**——否则无法判定。
4. **数量不必多，但要稳定**：20–50 条足够做回归；关键是**每次评估用同一份**。
5. **把失败样例单独记录**——归因比通过率更有价值。

## 四、检索侧指标（可离线、可程序化）

以 `k` 为截断位置（通常 3–5），给定一条黄金样例：

| 指标 | 定义 | 直觉 |
|:-----|:-----|:-----|
| **Hit@k** | 前 k 条里**至少有一条**来自期望来源 → 1，否则 0 | "有没有捞到" |
| **MRR** | 首个正确结果的排名 `r` 取 `1/r`，对所有样例求均值 | "捞得够不够靠前" |
| **Source Recall** | `命中的期望来源数 / 期望来源总数` | "该捞的都捞到了吗" |
| **Keyword Coverage** | `命中关键词数 / 期望关键词总数` | "捞到的内容对不对" |

nDCG@k 稍复杂，它按位置给命中打折（越靠后权重越低）：

```text
DCG@k  = Σ_{i=1..k}  rel_i / log2(i + 1)      # rel_i 为第 i 条的相关性(0/1)
IDCG@k = 理想排序下的 DCG
nDCG@k = DCG@k / IDCG@k                        # 归一到 0–1
```

**为什么 MRR 与 Hit@k 要一起看？** Hit@k 说"有没有"，MRR 说"排第几"。命中但排第 5，对上下文预算紧张的 RAG 来说几乎等于没命中。

## 五、生成侧指标（LLM-judge 作为补充）

检索再好，模型也可能**无视上下文、自由发挥**。这就是忠实度（Faithfulness）要抓的问题。

**做法**：让一个（通常更强的）模型判定"回答是否完全基于给定上下文"。

```python
# 需要 API Key；仅作补充，不可替代程序化判定
def judge_faithfulness_llm(question: str, context: str, answer: str) -> float:
    """返回 0–1：1=完全忠于上下文，0=大量编造。"""
    import os

    from langchain_openai import ChatOpenAI

    llm = ChatOpenAI(
        model=os.getenv("LLM_MODEL_NAME", "gpt-5.5"),
        api_key=os.getenv("LLM_API_KEY"),
        base_url=os.getenv("LLM_BASE_URL"),
        temperature=0,
    )
    prompt = (
        "请判断「回答」是否完全基于「上下文」，不得引入上下文之外的信息。\n"
        "只输出一个 0 到 1 之间的小数。\n\n"
        f"【问题】{question}\n【上下文】{context}\n【回答】{answer}\n"
    )
    raw = llm.invoke(prompt).content
    try:
        return max(0.0, min(1.0, float(str(raw).strip())))
    except ValueError:
        return 0.0
```

> ⚠️ **使用 LLM-judge 的三条纪律**：① 固定 prompt 与模型版本；② 抽样人工复核，确认 judge 本身靠谱；③ 把它当**趋势指标**，不要当绝对分数。

成熟的评估框架（如 RAGAS）已经内置了 Faithfulness / Answer Relevance / Context Precision 等指标，可直接调用；见 [8.7 评估工具](../08-生态与选型/生态调研/07-评估工具.md)。

## 六、实战：跑通 `eval.py`

配套示例 [`examples/05-rag-kb/eval.py`](../../examples/05-rag-kb/eval.py) 用**离线 BM25 通道**跑一遍检索侧评估，**无需任何 API Key**：

```bash
cd examples/05-rag-kb
python eval.py
```

输出形如：

```text
RAG 检索评测（离线 BM25 通道，k=4）
==============================================================================
 #  问题                         命中   排名   来源召回     关键词
------------------------------------------------------------------------------
 1  Atlas 产品由哪个区负责？            ✅    1    1.00     1.00
 ...
10  既受《数据合规政策》约束、又由华东区负责的是哪个…  ✅    1    1.00     1.00
------------------------------------------------------------------------------
Hit@4 = 100.00%   MRR = 1.000   Source Recall = 100.00%   Keyword Coverage = 100.00%
```

> ⚠️ **别被满分骗了**：这个示例语料**只有 3 篇文档**，指标接近满分是**正常**的——它验证的是**流水线正确**（切分、检索、父块回溯都通），而不是**检索能力上限**。
>
> 把 `data/` 换成你的**真实语料**（几百上千篇），数字才会立刻变得有信息量，优化也才有方向。

**读指标的正确姿势**：

| 现象 | 可能原因 | 先去调什么 |
|:-----|:---------|:-----------|
| Hit@k 低 | 召回不足 | 切分粒度、`k`、混合检索权重 |
| Hit@k 高但 MRR 低 | 正确结果排太后 | 重排（Rerank）、查询改写 |
| 检索指标高但回答差 | 生成没用好上下文 | 提示词、上下文拼装、模型 |
| 忠实度低 | 模型在编 | 提示词约束"仅基于上下文"、降低温度 |

## 七、把评估接进 CI（回归阻断）

评估最大的价值不是"测一次"，而是**每次改动都测**——防止"改 A 坏 B"。

```yaml
# .github/workflows/rag-eval.yml（示意）
name: rag-eval
on: [pull_request]
jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - name: 离线检索评测
        working-directory: examples/05-rag-kb
        run: python eval.py
      # 生产做法：让脚本在指标低于阈值时以非 0 退出，从而阻断合并
```

> 🔗 完整的 CI 门禁设计（测试 + 评测回归 + 灰度发布）见 [7.4 CI/CD 流水线](../07-生产部署/04-CICD流水线.md)；Harness 级的评测与可观测性见 [9.11 Harness 评测与可观测性](../09-驾驭工程/11-评测与可观测性.md)。

**推荐的门禁阈值**（示例，按业务定）：

| 指标 | 建议下限 | 说明 |
|:-----|:--------:|:-----|
| Hit@5 | ≥ 0.85 | 低于此值说明召回明显退化 |
| MRR | ≥ 0.60 | 排名质量底线 |
| Faithfulness | ≥ 0.90 | 编造容忍度极低 |

## 八、常见误区

| 误区 | 为什么错 | 正确做法 |
|:-----|:---------|:---------|
| "人看着还行" | 肉眼会被流畅的编造骗过 | 黄金集 + 量化指标 |
| 只测检索、不测生成 | 检索好不代表回答好 | 两侧分开测 |
| 只测生成、不测检索 | 出了问题不知道该修哪 | 先定位是检索还是生成 |
| 黄金集一次写死、永不更新 | 真实问题会漂移 | 定期补充线上 badcase |
| 拿 LLM-judge 当唯一标准 | 偏差 + 不可复现 | 程序化优先，judge 补充 |
| 只在本地测、不进 CI | 回归无人拦截 | 接进 CI 做门禁 |

## 本章小结

| 要点 | 说明 |
|:-----|:-----|
| 🎯 | RAG 的"好"必须**量化**；凭感觉调的优化大概率是自我安慰 |
| 🧭 | 评估要**分段**：检索侧（可程序化）与生成侧（部分需 LLM） |
| 📏 | 检索侧核心指标：**Hit@k / MRR / Source Recall / nDCG** |
| 🧪 | **黄金集**是评估的地基：真实问题 + 明确答案 + 覆盖多跳与负样本 |
| ⚖️ | **程序化判定优先**，LLM-judge（Faithfulness 等）只作补充 |

## 📝 课后练习

1. **✅ 基础**：运行 `python eval.py`，把输出里的 10 条样例逐条对照 `data/` 的原文，确认"命中"判定是否符合你的直觉。
2. **💡 进阶**：往 `GOLDEN` 里加 3 条**负样本**（语料里没有答案的问题），并思考：该用什么指标判断系统"该拒答"？给出你的判定规则。
3. **🚀 挑战**：给 `eval.py` 增加 `nDCG@k` 指标，并对比 `k=1 / 3 / 5` 时 MRR 与 nDCG 的变化，解释差异来源。
4. **🔍 探索**：把 `data/` 换成你自己的 20+ 篇文档，重跑评估。指标从 100% 掉到多少？据此判断哪一类问题最需要优化（召回 or 排名）。
